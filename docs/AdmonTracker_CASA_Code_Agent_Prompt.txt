3. Immediate findings to reproduce and fix

A. Staff identity collisions — treat as urgent until ruled out

At the reviewed commit, utils/access_control.py:user_access_from_secrets strips everything after @ and assigns access using the email prefix. A local test using a synthetic configuration assigned the same Manager role to reviewer_demo@approved.example and reviewer_demo@unapproved.example. This was a code-level reproduction, not a live unauthorized login.

Trace the full current OIDC and authorization path, including any upstream restrictions. Remove prefix-based authorization and any fallback that silently restores it. Prefer an explicit mapping from validated issuer/sub identity to approved staff role/project. If full verified email allowlisting is an interim migration choice, document its limitations, define secure enrollment/binding, and prevent automatic privileged account linking. Do not use a login UI domain hint as the security boundary.

Plan a controlled migration of the existing staff assignments so approved staff are not silently locked out or granted wider roles. Clarify actual approved accounts through existing records; do not guess their domains. Test same-prefix/different-domain accounts, unknown accounts, absent or invalid required identity claims, changed roles, revoked access, role escalation, and project isolation. Authentication by Google alone must not grant access to research data.

B. Secret version destruction — treat as urgent until ruled out

At the reviewed commit, utils/secret_store.py:GoogleSecretStore.destroy_versions searches for "enabled" inside str(version.state). SecretVersion.State is a proto enum backed by IntEnum; Python 3.11+ string conversion is numeric. The repository specifies Python 3.11. An isolated reproduction on Python 3.12 with a matching numeric enum made zero destruction calls for enabled/disabled versions. The deployed SDK and actual Secret Manager state were not checked in that review.

Reproduce with the real SDK type and deployed dependency versions. Replace fragile string matching with explicit supported enum comparisons. Define the intended treatment of both ENABLED and DISABLED versions for participant-token erasure; disabled secrets still retain data. Handle already-destroyed and unexpected states explicitly. Account for any configured delayed-destruction behavior and distinguish scheduled destruction from completed destruction.

Use mocks for unit tests and, after confirming an isolated test resource and authorization, a disposable synthetic secret for integration verification. Read back version states, verify access is rejected as expected, and record incomplete results honestly. Do not delete shared runtime/client secrets when deleting a participant's token. Avoid falsely displaying successful deletion when cleanup was skipped or failed. Do not mass-delete old production versions as part of the code fix.

C. Disconnect must stop local collection even when external services fail

Inspect utils/connection_management.py, token stores, registry updates, cache behavior, all collectors, and in-flight jobs. In the reviewed code, disconnect can attempt to load a secret before recording local disconnection, so a Secret Manager error may interrupt the flow. Determine current behavior rather than assuming revocation always works.

Design idempotent local collection blocking and durable revocation/cleanup status, with bounded retries for external operations. A remote revocation failure must not leave collection authorized locally. Prevent refresh races, stale caches, retries, or the legacy bridge from reactivating a disconnected connection. Inspect job checks before provider access and archive writes. Surface partial failure without leaking provider responses or claiming erasure is complete.

4. Other security work, prioritized by demonstrated risk

Assign P0 to a credible unauthorized-access/data-exposure path or failure to honor an immediate withdrawal; P1 to other applicable assessment blockers; P2 to useful hardening without a demonstrated blocking requirement. Adjust these labels with evidence. Separate confirmed defects, unverified concerns, configuration gaps, and documented external dependencies.

Authorization and isolation:
- Verify server-side checks at actual read/write boundaries for Admin, Manager, Student, Guest, and anonymous users. Confirm the intended Student capabilities instead of inferring them from the role name.
- Test direct page access, altered watch/project identifiers, cross-project reads/writes, cache isolation, account switching, and stale sessions. Hidden navigation and disabled widgets are not sufficient authorization.
- Confirm the guest demo cannot reach real data, provider APIs, or writes.
- Firestore server-client access relies on IAM rather than browser Security Rules; assess both appropriately for the actual architecture. Do not claim restrictive browser rules protect an overprivileged server service account.

Participant links and OAuth:
- The reviewed management link carries a bearer token in the URL and defaults to 365 days. Hashing it in storage does not protect browser history, referrers, screenshots, or request logs.
- Evaluate a short-lived, single-use link exchanged for a properly protected session, or another justified design that preserves participant withdrawal access. Assess replay, expiry, reissue/recovery, rate limits, referrer/cache behavior, and infrastructure logging. Distinguish necessary OAuth callback parameters from long-lived application bearer credentials.
- Bind management authority to a specific enrollment/connection lifecycle. Check whether an old link could affect a different participant after a watch is reused or reconnected.
- Review state validation, consent/version checks, redirect allowlists, provider endpoints, and optional PKCE support. Do not assert PKCE is universally mandated for every confidential-client flow without checking applicable requirements.
- In the reviewed state flow, validation and consumption are separate operations. Test concurrency and implement atomic consumption where needed; an append-only usage record alone is not proof of atomic replay protection.
- Validate actual granted scopes, partial grants, cancelled authorization, refresh/revocation errors, and reauthorization. Do not broaden scopes to simplify the assessment.

Sessions and administrative MFA:
- Verify MFA enforcement for application administrative access and privileged infrastructure accounts. Google SSO by itself is not evidence of enforced MFA. Establish what can actually be enforced for institutional versus personal accounts.
- Review idle/absolute timeout, server-side revocation, privilege-change invalidation, and simultaneous tabs/devices. Streamlit 1.56 documentation describes a 30-day identity cookie and existing tabs retaining their st.user state after logout elsewhere; verify your deployed behavior and close relevant gaps.
- Inspect Secure/HttpOnly/SameSite attributes, HTTPS redirects, CSRF/CORS protections, and WebSocket origin handling. Preserve working Google OAuth and Streamlit behavior. Avoid adding a generic CSP or proxy change without testing compatibility.

Secrets, dependencies, and deployment:
- Verify actual production SECRET_MANAGER_ENABLED=true and ALLOW_PLAINTEXT_SECRET_FALLBACK=false. The reviewed generator/defaults allow plaintext during staged migration. Prefer a clear production fail-closed configuration while retaining explicitly supported legacy behavior where necessary.
- Check plaintext remnants in Sheets, Firestore, exports, deployment outputs, logs, notebooks, and Git history using redacted reporting. If exposed credentials are found, stop their disclosure, assess impact, and prepare rotation/cleanup for approval.
- Review effective service-account permissions, human access, Shared Drive inheritance/sharing, GitHub/Heroku access, logs/add-ons, and bootstrap-key handling. Recommend narrowly scoped permissions without assuming IAM labels alone establish least privilege.
- Inventory the exact deployed dependency graph and runtime/build environment. requirements.txt currently has many loose constraints; a scan of newly resolved local packages does not prove the deployed release is safe. Use appropriate SCA/SAST/secret-scanning tools and retain reproducible versions/reports. Do not invent CVEs or blindly upgrade everything.
- Review user-controlled inputs reaching HTML, email, URLs, filenames, file uploads, dynamic execution, and external requests. Assess actual reachable paths, including relevant legacy code.
- Check TLS, security headers, public errors/debug output, DNS/custom domains, and safe rollback. Replacing the framework, hosting provider, or entire authentication stack is not the default; propose it only if needed to solve a demonstrated requirement.

5. Retention, withdrawal, and all copies of data

The current project memory says the approved Google Health addendum permits one month of collection plus up to one additional month for processing/quality checks, with withdrawal stopping collection and requiring deletion unless separate explicit retention consent is obtained. Verify the exact approved text. These commitments are not a generic CASA retention rule.

The reviewed implementation records deletion requests and relies on manual completion; it does not establish automated end-to-end erasure or scheduled one-month deactivation. A manual procedure may be acceptable if it is operational, timely, and evidenced. Do not label automation itself mandatory without a basis.

Map measurement data, operational status containing health values, identity links, tokens and historical versions, raw archives, recovery copies, downloaded/derived datasets, mailbox copies, temporary files, caches, backups, revision history, and legal/administrative records. Alert email code can include a heart-rate value, so mailboxes need an explicit place in the data map and retention/minimization decision. Distinguish operational deletion from provider-side retention and document technical limits honestly.

Propose a practical workflow with ownership, deadlines, collection-stop enforcement, retry/exception handling, and auditable completion. Use enrollment identifiers rather than deleting everything ever associated with a reusable watch. Avoid recording deleted health values in the deletion audit. Clarify whether the current "request deletion" action also means withdrawal and should stop collection, since it is separate from "disconnect" in the reviewed UI.

Ask me only for unresolved policy decisions such as which approved retention rule applies to each study/provider, how historical data are covered, who approves exceptions, and who executes manual tasks. Do not change signed consent, shorten research retention arbitrarily, or execute deletion on real participants to demonstrate readiness.
